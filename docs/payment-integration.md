# 微信支付与站内余额接入边界

核对日期：2026-11-03。本文记录官方产品能力和项目实现约束，不替代微信支付对具体主体、类目、经营场景的审核结果。

## 当前项目条件

- 用户计划：烟台首版，多个代购商入驻，自提及到家，代购费 6%，称重商品按实际重量多退少补，未成团金额退入小程序内部余额。
- 用户当前运营主体为“个人”；用户最新明确尚未申请小程序 AppID；尚无微信支付商户号。
- 开发阶段可以完成业务界面、多商户数据隔离、订单、称重差额、内部余额账本和模拟流程。当前不能把模拟支付、内部余额入账或模拟退款展示成已完成的真实微信资金操作。

## 1. 个人主体与当前上线阻碍

微信支付《小程序支付·开发接入准备》（2026-10-16）列明可申请小程序支付权限的主体为：个体工商户、企业、事业单位、政府机关、社会组织，并要求小程序认证、商户号权限和 AppID 授权绑定。[官方接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4015459512)

腾讯 CloudBase 当前官方小程序开发说明进一步明确：个人主体小程序不能绑定微信支付商户号用于实物商品或线下服务；个人主体在特定类目下的“虚拟支付”是另一产品，不适用于本项目食品/代购交易。[CloudBase 官方说明](https://docs.cloudbase.net/ai/cloudbase-ai-toolkit/prompts/miniprogram-development)、[虚拟支付与实物支付区别](https://docs.cloudbase.net/integration/wechat-virtual-pay)

因此，“此前按个人主体规划、尚无 AppID 和商户号”的现状尚不满足本项目真实小程序付款条件。可以继续本地开发、开发工具模拟、后端与管理功能建设；真实支付、退款、分账和多代购商结算须待符合条件的主体及相应支付能力就绪后联调。不能以有 AppID 推定支付资格已具备。

平台收付通允许部分“小微”“个人卖家”作为二级商户入驻，是针对平台下商户的规则，不能理解为用户本人可以凭个人小程序直接成为支付平台。官方对个人卖家另有明确条件，须逐项按进件要求核验。[平台接入准备](https://pay.wechatpay.cn/doc/v3/partner/4012086921)

## 2. 多代购商的支付模式

| 模式 | 官方产品含义 | 对本项目的影响 |
| --- | --- | --- |
| 普通商户直连 | 商户自己收款，微信支付结算到该商户账户 | 适合确定的单一真实收款商户；不能仅靠应用数据库增加 merchantId 就视为多个入驻代购商已完成独立收款及结算 |
| 普通服务商 | 服务商代特约商户接入；收款主体是特约商户，资金到子商户结算账户，服务商账户不直接收款 | 需服务商资格、特约商户进件、相应产品授权及 AppID 场景关系 |
| 平台收付通 | 基于服务商模式，为平台电商设计，平台协助二级商户入驻；可合单支付并进行账期、佣金分账 | 最贴近多代购商入驻及跨商户购物车的候选路线；必须先完成服务商入驻、工具箱开通、平台审核、AppID 绑定及二级商户进件 |

官方来源：[接入模式](https://pay.wechatpay.cn/doc/v3/partner/4012081931)、[平台收付通产品介绍](https://pay.wechatpay.cn/doc/v3/partner/4012086891)、[平台收付通接入准备](https://pay.wechatpay.cn/doc/v3/partner/4012086921)。

实施时应拆分业务父订单与每个代购商的子订单，并把支付收款主体、商户号、订单金额、退款和分账关联到子订单。支付适配层保留模式配置，未配置商户能力时关闭真实支付。用户收费中的“代购费 6%”不自动等于平台分账佣金；代购商与平台各自收入归属仍需业务定义。

## 3. 微信退款与“小程序内部余额”是两套记录

微信标准订单退款 API 的官方资金路径为原支付账户，例如银行卡退银行卡、微信零钱退微信零钱；支持全额或部分退款。它不会把款项写入本项目自己的余额数据库。[订单退款产品介绍](https://pay.wechatpay.cn/doc/v3/merchant/4013071001)

用户要求的未成团退至“小程序余额”，可以先建设为独立的站内余额账本业务流程，但应满足以下技术区分：

- 明确标为“站内余额”，不称“微信零钱”，不展示为已经通过微信退款 API 完成。
- 订单记录分别保存原微信实收、实际微信退款、内部余额入账及已消费金额。内部余额入账不伪造微信退款单号或退款成功通知。
- 同一退回金额只执行选定的一条资金处理路径，防止既原路退款又重复增加可消费余额。
- 每条余额入账、冻结、扣减、解冻、冲正保留不可重复的业务单号、关联订单、来源商户、发生时间与操作原因；使用数据库事务与幂等约束防止重复入账和并发超扣。
- 多代购商之间是否通用余额、由谁承担该余额、如何与各代购商结算，必须在真实启用前确定。数据层保留来源商户和余额责任主体，不能默认跨商户通兑已由微信支付提供。
- 本轮可做开发账本及测试数据；真实收款后的余额资金处理方案应与最终支付产品、主体和商户开通结果一致后再启用。

若改用微信原路退款，须以后端退款通知或查单确认成功，不能以“退款接口已受理”当作“已到账”。官方还说明：已分账资金不会因退款自动回退，需另外安排分账回退及退款出资。[退款开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)、[平台申请退款](https://pay.wechatpay.cn/doc/v3/partner/4012476892)

## 4. 称重多退少补

后端保留预估重量、实际重量、计价单价、计费规则版本、称重证据、预收金额、最终应收和差额。金额统一按整数分运算并记录舍入规则。

- 少收：创建关联原订单的补款单，由用户主动调起微信收银台支付；不把用户先前付款当作可任意追加扣款授权。
- 多收：按选定的站内余额退回流程或真实微信部分退款流程处理，清楚记录实际采用的路径。
- 合单支付的退款须关联具体子单，不凭父订单总号把所有商户资金混在一起处理。

付款由后端创建预支付单，小程序使用 wx.requestPayment 调起微信收银台。支付是否成功以后端验签通知与主动查单为准；前端返回成功不能单独决定履约。[微信支付开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791911)、[小程序调起支付](https://pay.wechatpay.cn/doc/v3/merchant/4012791898)

## 5. 后续需要的配置和业务决定

1. 实际 AppID 字符串、对应注册主体/认证状态、用户在该 AppID 下的开发者权限。
2. 最终收款模式和符合该模式的运营主体；若采用平台收付通，提供服务商/平台开通结果与二级商户进件安排。
3. 商户号、AppID 绑定及产品权限结果。私钥、APIv3 密钥等只配置在服务端安全环境，不写入小程序代码或 Git；不在聊天中索取密钥明文。
4. 正式后端域名、HTTPS 和微信合法域名配置；支付与退款可访问的通知地址。
5. 6% 代购费最终归属、平台佣金规则；站内余额是否跨代购商使用、余额责任主体、退款/提现及余额关闭后的处理规则。
6. 称重差额确认时点、补款未付时的履约方式、失败拼单截止时点、退款与余额状态文案。

没有执行商户开户、产品申请、账号登录、真实付款、退款或分账。
